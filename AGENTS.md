# AGENTS.md

The engineering contract for anyone, human or AI agent, changing Khata. Read it before writing code. [`DESIGN.md`](DESIGN.md) is the design contract shared by every Aback product; this file is the contract for this repository.

## 1. What Khata is

Khata is a Splitwise-style app for shared expenses: groups, one to one hisabs between two people, and its signature feature, a **private hisab inside a group**: an expense or payment between two members that the rest of the group never sees.

- Production: `https://khata.aback.ai` (one Cloudflare Worker, one D1 database)
- License: MIT. The Khata and Aback names and marks are not covered by it.

## 4. Repository layout

```
src/
  domain/          Pure money logic: amounts, splits, balances, debt simplification. No I/O.
  server/
    db/            Drizzle schema (the single source of truth), client, batch helper
    auth/          Better Auth instance and the session helpers pages use
    email/         The mailer over the send_email binding, and the email templates
    services/      Business rules and data access, one file per area. Every rule lives here.
    actions/       Server Actions: parse input, check the session, call a service, revalidate
    queries.ts     Read models for pages (overview, group page, person page, feed)
    env.ts         Worker bindings and background work (waitUntil)
  app/             Routes. Pages are thin: load a read model, render components
  components/      UI components. Client components only where there is interaction
  lib/             Code shared by server and browser: validation schemas, labels, formatting
migrations/        SQL generated by drizzle-kit, applied by Wrangler
tests/             Service integration tests against D1 in Miniflare
```

Dependencies point one way: `app` and `components` use `server` and `lib`; `server/services` use `domain`, `server/db` and `lib`; `domain` uses nothing. A component never imports a service directly; it calls a Server Action.

## 5. Rules that keep the money right

1. **Money is an integer in the currency's minor unit** (paise, cents, yen). Never add, split or compare floating point amounts. Parse what people type with `parseAmount`, format with `formatMoney`.
2. **Splits always add up exactly.** `computeSplit` and `allocate` hand out rounding leftovers one minor unit at a time (largest remainder). Never write your own division.
3. **The server recomputes everything.** Forms send what people typed; services parse it and compute every share again. Client previews use the same `src/domain` functions, so they match.
4. **Currencies are never converted.** Every balance is a `MoneyByCurrency` map.
5. **Every multi-row write is one `db.batch`** (`runBatch`). D1 has no interactive transactions; a batch is atomic.
6. **Rows people can see are soft deleted** (`deleted_at`), so the activity feed can still name them.
7. A change to `src/domain` needs a test in the matching `*.test.ts`.

## 6. Visibility: who can see what

This is the most important invariant in the codebase. Every expense, payment and activity row has a `visibility`:

| Visibility | `group_id` | Who can see it |
| --- | --- | --- |
| `group` | set | Active members of that group |
| `pair` | set | Only `pair_a` and `pair_b` (a private hisab inside a group) |
| `pair` | null | Only `pair_a` and `pair_b` (a one to one hisab) |

Rules:

- `pair_a < pair_b`, always. Use `orderedPair()`.
- A pair row can only involve its two people, and the person creating it must be one of them.
- Pair rows **never** count toward a group's shared balances, debts, CSV export, or the group feed of other members.
- The visibility conditions live in one place, `src/server/services/ledger.ts` (and the same rule in `activity.ts`). Do not write a new query for expenses or payments that bypasses them.
- When someone may not see a thing, answer **not found**, never forbidden. A response must not confirm that a private row or a group exists.
- `tests/services.test.ts` has a `private hisab inside a group` suite. Any change near visibility must keep it passing, and new read paths need a test there.

## 7. People and accounts

- Sign in is passwordless: Google, or a six digit code sent by email (10 minute expiry, five attempts, stored hashed).
- People can be added by email before they ever sign in. That creates a `user` row with `email_verified = false` and no credentials (a placeholder). The first sign in with that address, by code or Google, takes the row over. This is why `account.accountLinking.requireLocalEmailVerified` is `false`: a placeholder has no way in to take over. Never add a sign-in method that could give a placeholder credentials without proving the email.
- `onboarded_at` is set on the welcome page. Signed-in pages call `requireOnboardedViewer()`.
- Deleting an account anonymises the row (other people's expenses point at it) and is only allowed when every balance is settled.

## 8. Security checklist for every change

- Every Server Action goes through `runAction`, which checks the session. Every service re-checks access (`requireMembership`, `requireConnection`, the pair checks). Never trust an id from the browser.
- Validate input with the Zod schemas in `src/lib/validation.ts`, on the server.
- Only `AppError` messages reach people. Anything else is logged and replaced.
- Redirect targets go through `safeNext()`.
- Emails escape everything a person typed (`escapeHtml`) and never contain secrets other than the sign-in code itself.
- Rate limits: sign-in codes per email and per IP, invitations and reminders per user, activity emails per actor.
- D1 allows 100 bound parameters per statement. Use subqueries, not long `IN (...)` lists; chunk when you must.

## 9. Design and copy

- Follow `DESIGN.md`. In short: square corners everywhere, neutral surfaces, Aback Blue (`primary-*` ramp) only as a signal, Geist, Tabler icons only, every light colour paired with its dark value, visible focus rings.
- Use `@aback-ui/ui` components before writing markup.
- Status colours always come with words: "you owe" in danger red, "owes you" in success green. Never colour alone.
- Copy is plain and specific, sentence case for messages. **No em dashes or en dashes anywhere** (UI, emails, docs, comments). Use a comma, a colon or a full stop. No exclamation marks, no emoji.
- Error messages say what happened and how to fix it.

## 10. Database changes

1. Edit `src/server/db/schema.ts`.
2. `bun run db:generate` writes `migrations/NNNN_name.sql`. Read it.
3. `bun run db:migrate:local`, then `bun run check`.
4. Deploying applies nothing by itself: run `bun run db:migrate:remote` before deploying code that needs the new schema. Migrations must be backward compatible with the code that is running.

Never edit a migration that has been applied to production.

## 11. Deploying

See [`docs/deployment.md`](docs/deployment.md). Production config lives in `wrangler.jsonc`; secrets (`BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) are set with `wrangler secret put` and never committed. `bun run deploy` refuses to run when the route, `APP_URL` and the email sender do not agree.

## 12. Definition of done

- `bun run check` passes.
- New behaviour has tests; visibility changes have privacy tests.
- The UI works at 375px and 1280px, in light and dark.
- `bun run check:copy` passes (no em or en dashes; it is part of `bun run check`).
- Docs updated when commands, env vars or behaviour change.
